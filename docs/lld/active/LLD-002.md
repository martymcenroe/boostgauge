### 2.5 Logic Flow (Pseudocode)

```
Initialization:
1. Read telltale_windows from config.
2. Initialize TelltaleSet with durations (short, medium, long, None).

On Update (timestamp, value):
1. For each telltale in TelltaleSet:
   - telltale.update(timestamp, value)

On Render (value, size):
1. Extract peaks = TelltaleSet.as_tuple()
2. Call boostgauge.skins.stingray.render(value, peaks, size)
3. Update tkinter Label with the composed Image

On Hover:
1. Generate tooltip text using format_tooltip_text(durations)
2. Show tooltip window with text

On Reset Menu Click (window_id):
1. IF window_id == "all" THEN
   - call reset() on all instances
   ELSE
   - call reset() on the specific Telltale instance
```

### 2.6 Technical Approach

* **Module:** `src/boostgauge/gauge.py`, `src/boostgauge/formatters.py`
* **Pattern:** Dependency Injection / Pure UI Logic separation
* **Key Decisions:** String formatters and mapping logic are completely isolated from `tkinter` to comply with Option C testing rules (no Tk instantiation in tests). Telltales maintain state but renderer takes pure values.

### 2.7 Architecture Decisions

| Decision | Options Considered | Choice | Rationale |
|----------|-------------------|--------|-----------|
| String formatting logic | In UI code, Pure functions | Pure functions | Ensures the dynamic formatting requirement (RS6, U1) can be tested cleanly without a Tk context. |
| None state representation | Convert to 0, Pass through | Pass through | #332 renderer is explicitly responsible for "None-not-drawn" decision. Wiring only passes data. |

**Architectural Constraints:**
- Must adhere strictly to Option C testing (no `tkinter.Tk()` in unit tests).
- Must compose over #332's `stingray.render` without re-implementing drawing rules or colors.

## 3. Requirements

1. The app shall instantiate four `Telltale` instances: three with durations from `telltale_windows.short`, `telltale_windows.medium`, `telltale_windows.long`, and one with window `None`.
2. The app shall feed every collector sample to all four instances via `update(timestamp, value)`, passing the exact same values.
3. The app shall pass all four `current_peak()` values to #332's renderer on every refresh as the four-slot telltales argument, passing `None` unaltered.
4. The short-window menu entry shall call `reset()` on the short-window instance, leaving others untouched.
5. The medium-window menu entry shall call `reset()` on the medium-window instance, leaving others untouched.
6. The long-window menu entry shall call `reset()` on the long-window instance, leaving others untouched.
7. The all-time menu entry shall call `reset()` on the all-time instance, leaving others untouched.
8. The "Reset All" menu entry shall call `reset()` on all four instances.
9. Menu entry labels shall derive from a pure formatter covering non-default durations (e.g. 90s -> 'Reset 90s', 900s -> 'Reset 15m', 7200s -> 'Reset 2h').
10. Hovering the gauge shall show a tooltip identifying each window by label and aesthetic color (cyan `#3BD7F0`, orange `#FF9A2E`, magenta `#D45BE8`, coral red `#FF6E7A`), derived from a pure formatter tested against non-default durations.
11. Render-tier tests shall assert the composed image end-to-end through #332's renderer via pixel classification against the palette rows.

## 4. Alternatives Considered

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| Formatters inside GaugeWidget | Tighter coupling | Cannot be tested without mocking or instantiating widget pieces. | **Rejected** |
| Pure Functions | Testable in isolation | Requires passing state around explicitly. | **Selected** |

**Rationale:** Option C testing mandates `tkinter` not be instantiated in tests. Pure functions are the only robust way to test dynamic label formatting over multiple configurations.
