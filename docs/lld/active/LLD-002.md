### 2.5 Logic Flow (Pseudocode)

```
1. ON init:
   - Create 3 Telltales with durations from config, 1 Telltale with None (all-time)
2. ON update(timestamp, value):
   - For each Telltale: call update(timestamp, value)
3. ON refresh:
   - Call current_peak() on all 4 instances
   - Pass tuple (p1, p2, p3, p4) to renderer, passing None unmodified
4. ON menu action (e.g. Reset 1m):
   - Call reset() on the corresponding Telltale instance
5. ON tooltip hover:
   - Call get_tooltip_text(config.short, config.medium, config.long)
   - Display returned string without altering it
```

### 2.6 Technical Approach

* **Module:** `src/boostgauge/telltale_group.py` and `src/boostgauge/labels.py`
* **Pattern:** Facade / Pure Formatters
* **Key Decisions:** Separating the formatting logic into `labels.py` keeps it pure and fully unit-testable without any `tkinter` instantiation (Option C per `docs/design/0001-test-strategy.md`). The `TelltaleManager` isolates the state and fan-out of the four instances, enabling testing of the wiring and None-pass-through using a recording double.

### 2.7 Architecture Decisions

## 3. Requirements

1. The application shall instantiate four Telltale instances: three with durations read from the configuration (`telltale_windows.short`, `telltale_windows.medium`, `telltale_windows.long`), and one with window `None` for all-time.
2. The application shall feed every collector sample to all four instances via `update(timestamp, value)`, passing the identical timestamp and value to each.
3. The application shall pass all four `current_peak()` values to the renderer as a four-slot argument on every refresh, passing `None` values through unfiltered.
4. The application shall provide a short-window reset action that calls `reset()` on the short-window instance and leaves the remaining three untouched.
5. The application shall provide a medium-window reset action that calls `reset()` on the medium-window instance and leaves the remaining three untouched.
6. The application shall provide a long-window reset action that calls `reset()` on the long-window instance and leaves the remaining three untouched.
7. The application shall provide an all-time window reset action that calls `reset()` on the all-time instance and leaves the remaining three untouched.
8. The application shall provide a 'Reset All' action that calls `reset()` on all four instances.
9. Menu entry labels shall derive from a pure formatter over the configured duration: short at 90s reads 'Reset 90s', medium at 900s reads 'Reset 15m', long at 7200s reads 'Reset 2h'. The all-time label is constant at 'Reset All-time'.
10. Hovering the gauge shall present a tooltip identifying each window, formatted as one line per window: '<window label> — <color name>', binding the exact names 'cyan', 'orange', 'magenta', and 'coral red'.
11. Tooltip window labels shall derive from the pure formatter covering all branches (e.g. 90s reads '90s — cyan', 900s reads '15m — orange', 7200s reads '2h — magenta').
12. Render-tier tests shall assert the composed image produced end-to-end through the real renderer with baseline-independent presence/absence detected by classifying sampled pixels against the aesthetic doc's palette rows (`cyan #3BD7F0`, `orange #FF9A2E`, `magenta #D45BE8`, `coral red #FF6E7A`), pinned by a self-generated baseline.
